# clowder - source documentation

This folder documents the source of `clowder`, one module at a time. Each file
under `clowder/` has a matching `.md` here, named after the source path (for
example `clowder/state.py` -> `clowder/state.py.md`). Two files outside the
package are documented too: `scripts/check.py` (the repo's gate runner) and
`extensions/diff.ts` (the `/diff` review extension).

No source file was changed to produce these docs. The docs were generated by a
sweep that read each file, wrote its page, and moved on. See `README` (this file),
`.sweep_progress.json` (what was done) and `.sweep_errors.log` (what failed).

## What clowder is

`clowder` is one front door for a crew of coding agents. A person talks to one
agent; that agent dispatches work to the others, keeps the state, and brings
answers back with their question attached. The design motto is in the package
docstring: "The spine is code. The agent is only the front."

The code is the bookkeeping layer. It decides which agent and which repo a task
belongs to, sends the brief, records the task, and reports the answer. Each task
runs in its own git worktree, so parallel changes to one repo cannot collide.

## The module map

The package is one installable command (`python -m clowder ...`) plus a script and
an extension. The modules fall into four layers.

### Entry and presentation

- `clowder/__init__.py` - package marker and `__version__`.
- `clowder/__main__.py` - `python -m clowder` entry point; calls `cli.main`.
- `clowder/cli.py` - the command line. The spine: `build_parser`, `main`, and one
  `cmd_*` handler per command. Every other module is reached from here.
- `clowder/report.py` - builds one report block in a fixed order (question, usage,
  answer, at most one open decision).
- `clowder/board.py` - generates the self-contained HTML board. Pure functions of
  the data handed to it.

### State and time

- `clowder/state.py` - the one JSON state file and its three record types: `Task`,
  `Job`, `Queued`, plus `StateStore` (atomic, concurrency-safe load/save).
- `clowder/sessions.py` - reads Pi session JSONL for real usage, cost and model.
- `clowder/timeutil.py` - one clock: ISO UTC strings and epoch numbers, parsed to
  comparable epochs, plus human age/duration labels.
- `clowder/audit.py` - the append-only audit file beside the state file.

### Adapters and infrastructure

- `clowder/mux.py` - the terminal-multiplexer adapter. Drives panes by agent name.
  The live agent list is the roster.
- `clowder/gitcmd.py` - git called directly: read state, worktrees, branches,
  merge, publish guards, and the `RiskMemo` cache.
- `clowder/topology.py` - makes sure an agent exists in the repo a job belongs to,
  derives safe names, prepares worktrees, writes remote-pi config.
- `clowder/config.py` - reads TOML config and environment overrides into one
  frozen `Config`.
- `clowder/load.py` - reads the machine's load (memory percent on Windows, load
  per CPU on Unix) for the optional heavy-step gate.
- `clowder/marker.py` - the dispatch marker prepended to every brief.
- `clowder/errors.py` - the error family, each carrying a process exit code.

### Repo tooling

- `scripts/check.py` - every gate in one place (smoke, lint, format, type, tests).
- `extensions/diff.ts` - the `/diff` Pi command: review one file at a time.

## How a dispatch flows

1. `cli.main` parses the command and calls `cmd_dispatch`.
2. `_context` loads `Config` (`config.py`) and opens a `StateStore` (`state.py`).
3. `_dispatch` resolves the repo, finds or checks the agent (`topology.ensure_agent`
   / `mux.list_agents`), and applies the guards (cross-repo, open work, heavy
   overlap, high load).
4. `marker.apply_marker` builds the exact text; `mux` delivers it (over the agent
   bus when configured, else typed under the input-box guard).
5. The new `Task` is saved to the state file (`state.py`), and the board is
   rewritten (`board.py`) because the command flagged `refreshes_board=True`.
6. Later, `cmd_report` reads the worker's Pi session (`sessions.py`) for usage and
   the answer, and `report.build_report` prints it. `cmd_inbox` lists everything
   that reported since the last look.

## How a job flows

A `Job` is one branch inside an agent's worktree, so the expensive install is paid
once per agent, not once per job. The owner gate is a chain, and each step is a
separate command:

1. `job open` - start the branch and open the writer's space.
2. `dispatch --job <id>` - the writer works.
3. `job handover` / `job pin` - pin the saved commit into the reviewer's copy.
4. `job pass` - record the owner's pass (bound to a commit).
5. `job sync` - merge `origin/<base>` forward, never rewriting the branch.
6. `job publish` - push, only after the pass.
7. `job merge` - merge the pull request, only after the separate merge word.

`job close` and `job merge` return the space to its base while keeping the
install. `state.Job.state_in_words` derives the state word from the record, so it
cannot drift from the pass and merge word the owner actually gave.

## State, concurrency and the board

- There is one state file. It is written atomically (temp file plus `os.replace`)
  under a file lock, and a save that finds a newer file folds other writers'
  records in or refuses a clashing edit loudly. A lost update is never silent.
- Unknown fields from a newer copy are kept in each record's `extra` and merged
  back on save, so versions can coexist.
- The board is a generated HTML file (`board.py`), not a live panel. It is a pure
  function of `BoardData`, so it is testable without a browser.
- The multiplexer's live agent list is the roster; there is no roster file.

## Reading order for a newcomer

1. `clowder/__init__.py`, `clowder/errors.py` - what the package is and how it
   fails.
2. `clowder/timeutil.py`, `clowder/state.py` - the data model.
3. `clowder/config.py`, `clowder/marker.py` - settings and the dispatch envelope.
4. `clowder/gitcmd.py`, `clowder/topology.py`, `clowder/mux.py` - the three
   adapters (git, agents, terminal).
5. `clowder/sessions.py`, `clowder/report.py` - reading an answer and formatting a
   report.
6. `clowder/board.py`, `clowder/audit.py` - the two views of the record.
7. `clowder/cli.py` - the spine that ties them together.

## Known source defect

`clowder/load.py` does not compile. Lines 51 and 64 use the invalid Python syntax
`except OSError, AttributeError, ValueError:`; multiple exception types must be
parenthesized. This was found while documenting and is recorded in
`.sweep_errors.log` and in `clowder/load.py.md`. The source was not changed,
because the brief makes the sweep read-only.

## Doc conventions

Each module page has:

- **Purpose** - what the module does, in plain language.
- **Public API** - classes and functions with signatures, parameter types and
  return values.
- **How It Works (internals)** - the private `_`-prefixed helpers, grouped under
  the public function that calls them, one line each. Helpers with no public
  caller are under an **Internal utilities** heading. Trivial presentation
  one-liners are skipped.
